# Build a Logic Model

Build or review a practical logic model from the files the user provides. A first run can start with an attached description, budget or resource list, activity notes, goals, and measures; no profile or setup command is required.

## Workflow

1. Inventory the source packet. Record source IDs only for supplied evidence, along with period, definitions, material gaps, and the supplied planning, learning, funding, or evaluation use. Track missing evidence with stable gap markers, never source IDs. If no use is supplied, ask what decision or learning question the model should support rather than inferring one. Read `../../references/source-and-consent.md`. Generalize person-linked row or case IDs unless an exact key is necessary for a staff-only correction; if retained, label it sensitive and ask staff to confirm its use.
2. Build the main model only from elements supported by the organization's sources. Do not fill a blank stage merely to make the model look complete. Show a useful placeholder such as `[NEEDS INPUT: staff-defined medium-term outcome]` when the organization has not selected that element. Use `[UNMEASURED]` only when an output or outcome is stated in a source but no usable measure or result was supplied.
3. Give each output and outcome a short label (a Model ID) such as `O1`, `ST1`, `MT1`, or `LT1`, then link the sourced path from resources to activities to those elements. Distinguish planned activities and targets from observed results.
4. Repeat each Model ID in the measurement plan so staff can see which measure belongs to which result. For every output and outcome, provide either a usable definition, data source, timing, numerator and denominator where relevant, owner, and limitation—or an explicit gap naming what staff still need to decide or supply. For each displayed rate/change, attach numerator, denominator, formula, unit or population, period, exclusions, and rounding. One unambiguous period heading may govern nearby measures with the same scope; repeat the period locally for comparisons, mixed current/cumulative results, or a measure likely to be reused alone. Check each measure separately for its source, collection/reporting timing, and owner: a gap for one does not resolve the others. Treat system existence, coverage of the needed data category, export or access method, cadence, and owner as separate claims. Support each claim from the packet; evidence that an organization uses a system does not establish that it contains the needed records, permits the proposed export, runs on a particular schedule, or has an assigned owner. If one of these is missing, name that exact gap and do not describe the combined process as operational. If a cadence is not supplied and implementation depends on it, label a suggested cadence as an option for staff decision rather than as the operating schedule. Check that collection fits the supplied staff capacity, systems, timing, data access, and participant burden; prefer an existing workable source, and make any unresolved feasibility constraint explicit. If evidence is missing, create a stable gap record such as `GAP-01 | NO SOURCE PROVIDED` and link the need to that marker; never register the gap as a source or cite a real source as though it supports missing evidence.
5. Test the causal links: identify unsupported leaps, dependencies, dose or capacity mismatches, and sourced factors outside the organization's control. For every supplied or adopted materially necessary assumption, risk, dependency, or external factor, name the specific activity-to-result or result-to-result link it affects and state the expected effect or uncertainty; do not leave factors in a detached generic list. An example in an external framework is not the organization's assumption unless supplied evidence adopts it. When sources describe differing participant, community, or partner perspectives or access barriers, attach them to the affected link and preserve who reported the view; do not silently treat one perspective as universal. If the sources identify an affected perspective or access assumption but do not supply enough to assess it, state how that limits the model and ask a specific staff question. Keep possible new outcomes, assumptions, external factors, or causal bridges out of the main model unless staff have already selected them. Use `[NEEDS INPUT]` when the grounded model needs one of these elements but the sources do not provide it.
6. When brainstorming would help, add a separate **Options for staff consideration** section. Put unsourced outcomes, assumptions, external factors, and causal bridges here. Label every item as a proposed idea, explain why it might matter, and ask staff whether to adopt it. Do not present these options as program facts, approved outcomes, or measured results.

When reviewing an existing model, preserve its useful structure without adopting unsupported claims as organization facts. Audit whether each program action is classified as an activity and each direct product, reach, or participation result as an output; flag a misclassification instead of silently preserving it. Put unsupported content in a clearly labeled **Existing draft under review** column or companion table, mark it unsupported, and name the source or staff decision needed to retain it. The existing draft is evidence of what the model currently says, not proof that its claims are true.

## Output

Return:

- a compact logic-model table with a Model ID for every output and outcome;
- a short explanation of the strongest links;
- a review section listing missing links, unsupported assumptions, and unmeasured outcomes;
- a measurement plan that repeats each Model ID and gives its definition, source, timing, numerator/denominator where relevant, owner, and known limitations or its actionable gap;
- the supplied intended use and the links, measures, or gaps most relevant to that use, or a specific question when the use is missing;
- `[NEEDS INPUT]` questions for decisions only staff can make.

Use plain language and the organization's preferred term for people served. Before returning the output, check that same term in the model, measurement plan, limitations, privacy language, questions, and headings; do not fall back to a conflicting generic label. Cite registered source IDs beside facts and gap markers only beside missing inputs. Include a note that a logic model expresses intended links; it does not prove that the program caused an outcome.

## Quality rules

- Do not turn participant-sessions into unique people without deduplication evidence.
- Do not claim that an activity caused an outcome merely because it appears earlier in the model.
- Do not hide weak assumptions in a polished narrative.
- Do not make up targets, resources, measures, or external factors.
- Do not turn a sourced system name into an unsupported workflow or treat it as proof of an export schedule or assigned role.
- Do not make up an output or outcome to complete a stage. Put a plain `[NEEDS INPUT]` placeholder in the main model and, when useful, put the idea in **Options for staff consideration**.
- Ask one useful question a careful program reviewer might notice beyond the checklist when the packet allows it.

## Example

For the fictional packet, a sourced path may read: `S1: $12,000 and 2 facilitators` → `S1: 8 weekly workshops planned` → `O1 · S3: 24 participants enrolled, 20 completed` → `ST1 · S3: 16 of 20 reported increased budgeting confidence (80%; exit survey)` → `MT1: [NEEDS INPUT: staff-defined medium-term outcome]` → `LT1 · S1: [UNMEASURED] six-month savings behaviour`.

The measurement plan must contain `O1`, `ST1`, `MT1`, and `LT1`. `MT1` needs an actionable staff decision rather than an invented behaviour. `LT1` may be marked `[UNMEASURED]` because the source states that outcome but supplies no six-month result. A possible bridge such as continued household-budget use may appear only under **Options for staff consideration — proposed idea**, pending staff adoption.
